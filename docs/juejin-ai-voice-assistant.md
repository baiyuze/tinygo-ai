# 用 ESP32-S3 和 TinyGo，从零搭一个硬件 AI 语音助手底座

> 目标不是再做一个网页聊天框，而是做一个真正放在桌面上的 AI 小设备：它能听你说话，把声音交给 AI 理解，再把回答用声音说出来。

这篇文章记录的是这个项目的第一阶段：我先用 ESP32-S3 + TinyGo 把硬件 AI 语音助手的“底座”跑起来。

![ESP32-S3 + ST7789V2 调试中的硬件原型](./assets/esp32-s3-ai-voice-assistant-prototype.jpg)

目前还没有做到完整语音对话，但已经完成了一个很关键的基础链路：设备启动、WiFi 配网、API Key 录入、Flash 缓存、屏幕状态显示、RGB 状态灯、调试页面。

这些东西看起来不如“AI 对话”酷，但它们决定了这个硬件项目能不能真正脱离电脑、脱离串口、放到桌子上稳定运行。

## 为什么要做一个硬件 AI 语音助手

现在大多数 AI 应用还是停留在浏览器、App 或命令行里。它们很好用，但总感觉少了一点“在场感”。

我想做的是一个更像真实设备的 AI 助手：

- 有麦克风，能直接录音。
- 有扬声器，AI 可以直接说话。
- 有屏幕，显示联网状态、识别内容、回答摘要或调试信息。
- 有 RGB 灯，用颜色表达状态，比如配网、聆听、思考、回答、错误。
- 不需要每次插电脑改配置，手机连上设备热点就能完成 WiFi 和 API Key 配置。

最终形态大概是这样：

```text
人说话
  -> 麦克风采集音频
  -> ESP32-S3 上传/转发音频
  -> AI 识别、理解、生成回答
  -> TTS 合成语音
  -> 设备扬声器播放
  -> 屏幕/RGB 显示当前状态
```

第一阶段我没有直接上麦克风和扬声器，而是先把设备底座打牢：网络、配置、存储、显示、调试。

## 当前已经实现了什么

当前固件烧录到 ESP32-S3 后，可以做到：

- 开机初始化串口、WiFi Radio、RGB 灯和 ST7789 屏幕。
- 屏幕先做红/绿/蓝自检，然后进入调试面板。
- 优先读取 Flash 中缓存的 WiFi 配置并自动联网。
- 如果没有缓存、缓存连接失败，或者按住 BOOT 强制配网，就开启设备热点。
- 手机连接 `tinygo-s3-setup` 热点后，访问 `http://192.168.4.1/`。
- 在网页里填写 WiFi 名称、密码和 AI API Key。
- 配置保存到 ESP32-S3 Flash 最后一个 4KB 扇区。
- 连接成功后 RGB 变绿，配网模式 RGB 变蓝，错误状态 RGB 变红。
- 可以通过 `/debug` 页面查看设备状态和最近日志。

也就是说，它现在已经不是一个只能靠串口调试的 Demo，而是一个可以独立配网、独立保存配置、独立展示状态的硬件原型。

## 硬件配置

当前阶段用到的硬件很简单：

| 硬件 | 规格 | 作用 |
| --- | --- | --- |
| ESP32-S3 开发板 | Flash >= 2MB | 主控、WiFi、运行 TinyGo 固件 |
| ST7789V2 屏幕 | 2.0 寸，240x320，SPI | 显示状态和日志 |
| WS2812 RGB 灯 | 板载或外接 | 用颜色显示设备状态 |
| USB 数据线 | 支持数据传输 | 烧录和串口日志 |
| 杜邦线/排针 | 常规即可 | 连接屏幕和外设 |

屏幕接线如下：

| 屏幕引脚 | ESP32-S3 引脚 |
| --- | --- |
| VCC | 3V3 |
| GND | GND |
| BL | 3V3 |
| CS | GPIO10 |
| DC | GPIO11 |
| RST | GPIO12 |
| SCL/SCK | GPIO13 |
| SDA/MOSI | GPIO14 |

其他固定引脚：

| 功能 | 引脚 |
| --- | --- |
| BOOT 强制配网 | GPIO0 |
| RGB 状态灯 | GPIO48 |

后面做语音版本时，还会继续加：

- I2S 麦克风，用来采集用户语音。
- I2S 功放或 DAC，用来播放 AI 语音。
- 可能会增加一个按键，用来控制录音开始/停止。

## 软件架构

项目用 TinyGo 写固件，整体结构比较直接：

```text
main.go
  -> app.Run()
      -> boot        BOOT 键长按检测，决定是否强制进入配网
      -> rgb         GPIO48 WS2812 状态灯
      -> display     ST7789V2 屏幕初始化、自检、调试面板
      -> wifi        STA/AP 模式切换、DHCP、网络栈轮询
      -> portal      HTTP 配网页面和 debug 页面
      -> store       Flash 扇区读写，保存 WiFi 与 API Key
      -> diag        全局状态、串口日志、屏幕/debug 页面数据源
```

启动流程是这样的：

1. `app.Run()` 初始化串口和 ESP32-S3 WiFi Radio。
2. 初始化 RGB 灯和 ST7789 屏幕。
3. 屏幕显示自检画面，确认接线和驱动正常。
4. 检查 BOOT 键是否长按，如果长按就强制进入配网。
5. 尝试读取 Flash 中保存的 WiFi 配置。
6. 如果配置可用，进入 STA 模式连接 WiFi。
7. 如果连接失败，进入 AP 模式，启动热点、DHCP 和 HTTP 配网页面。
8. 用户提交配置后写入 Flash，再尝试连接 WiFi。
9. 设备状态同步输出到串口、屏幕、RGB 灯和 debug 页面。

## 为什么先做配网和状态系统

嵌入式 AI 项目很容易一上来就冲着模型、语音识别、TTS 去。

但如果设备连不上网、API Key 没地方填、失败了不知道哪里错、换个 WiFi 就要重新烧录，那它就很难从 Demo 变成真正能用的设备。

所以我先解决几个底层问题：

- **配网**：设备没有键盘，必须能让手机来配置 WiFi。
- **缓存**：WiFi 和 API Key 不能每次重启都重新填。
- **状态可见**：没有显示和灯光，硬件调试会非常痛苦。
- **强制恢复**：WiFi 写错了，必须能通过 BOOT 键重新进入配网。
- **网页调试**：设备脱离电脑后，仍然能查看最近日志。

这几个基础能力做好以后，后面接入录音、AI 和播放，才会比较顺。

## 配网是怎么做的

设备启动后会先尝试读取 Flash 缓存：

```text
Flash 有配置
  -> 尝试连接 WiFi
  -> 成功：进入正常模式
  -> 失败：进入热点配网

Flash 无配置
  -> 开启 tinygo-s3-setup 热点
  -> 手机访问 192.168.4.1
  -> 提交 WiFi 和 API Key
  -> 写入 Flash
  -> 尝试连接 WiFi
```

配网页面非常轻量，因为它要直接嵌入固件：

- WiFi 名称
- WiFi 密码
- AI API Key
- 保存并连接按钮

AP 模式下设备自己提供 DHCP，手机连上热点后可以直接访问：

```text
http://192.168.4.1/
```

如果设备已经连上家里的 WiFi，也可以访问：

```text
http://设备IP/debug
```

这个 debug 页面会展示当前模式、SSID、IP、是否收到 API Key、缓存状态和最近日志。

## Flash 缓存设计

当前配置保存在 Flash 最后一个 4KB 扇区里。

保存内容包括：

- WiFi SSID
- WiFi Password
- AI API Key

为了避免读到脏数据，记录里加了：

- magic 标识
- version
- SSID/password/API Key 长度
- checksum

这不是一个复杂数据库，只是一个适合当前阶段的轻量配置存储。

需要注意的是，API Key 当前还是明文保存在 Flash 中。作为原型验证可以接受，但如果后面要做成可长期使用的设备，需要考虑更安全的凭据管理。

## 屏幕和 RGB 的作用

硬件项目里，状态反馈很重要。

当前屏幕启动时会先显示红、绿、蓝自检，用来确认屏幕驱动和接线是否正常。之后进入调试面板，显示：

- 当前 WiFi 模式
- 当前 SSID
- 当前 IP
- 最近日志
- 缓存状态
- 错误信息

RGB 灯则负责一眼能看懂的状态：

| 颜色 | 状态 |
| --- | --- |
| 蓝色 | 配网热点模式 |
| 绿色 | WiFi 已连接 |
| 红色 | 错误 |

后面语音助手版本里，我还想继续扩展灯效：

- 呼吸蓝：正在等待唤醒
- 青色：正在录音
- 黄色：AI 正在思考
- 绿色：正在播放回答
- 红色：网络或 API 错误

## 构建和烧录

当前项目使用 Go + TinyGo。

依赖主要有：

- `tinygo.org/x/espradio`
- `tinygo.org/x/drivers`
- `tinygo.org/x/tinyfont`
- `github.com/soypat/lneto`

烧录命令示例：

```bash
go mod download
tinygo flash -target=ESP32-S3-generetor -port=/dev/tty.usbmodemXXXX .
```

串口日志：

```bash
screen /dev/tty.usbmodemXXXX 115200
```

这里的 `-target` 要使用当前硬件对应的 TinyGo target。我的这块硬件使用的是 `ESP32-S3-generetor`。

## 成本估算

这个项目的一个目标是低成本可复制。

按常见散件价格估算：

| 项目 | 估算单价 |
| --- | --- |
| ESP32-S3 开发板 | 25-60 元 |
| 2.0 寸 ST7789V2 SPI 屏幕 | 18-45 元 |
| 杜邦线/排针/小面包板 | 5-20 元 |
| 外接 WS2812 RGB 灯 | 1-5 元 |
| 外壳、螺丝、亚克力或 3D 打印件 | 10-50 元 |

当前最小原型大概 50-130 元能跑起来。后面加入麦克风、功放和扬声器后，成本还会增加一些，但整体仍然是一个很适合折腾的硬件 AI 项目。

AI 云服务费用另算。目前项目只是录入和保存 API Key，还没有真正发起 AI 请求。

## 总结

这一步做完以后，项目还不能和人完整对话，但它已经具备了一个硬件 AI 助手最基础的生命体征：

- 能启动。
- 能联网。
- 能配置。
- 能保存。
- 能显示状态。
- 能脱离电脑排查问题。

接下来真正有意思的部分才开始：让它听见声音，把声音交给 AI，再把 AI 的回答从扬声器里说出来。

如果从软件视角看，这是一个 TinyGo 嵌入式项目；如果从产品视角看，它是一个桌面 AI 语音助手的第一块地基。
